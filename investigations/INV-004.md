# INV-004: Scheduled task creation not logged by Sysmon (SC-003)

## What happened
Created a scheduled task with schtasks.exe (technique T1053.005), then
deleted it. Searched Sysmon's Operational log on win-client directly in
Event Viewer, from the very first event to the end, for any mention of
"schtasks". No match found anywhere in over 6,000 events.

## Investigation
- Confirmed the task was genuinely created and deleted (both commands
  returned SUCCESS in PowerShell).
- Searched Wazuh's Discover for the same string: no results.
- Searched Windows' own Security log for Event ID 4698 (scheduled task
  created): also empty, as predicted in the scenario card, since that audit
  subcategory isn't enabled by default.
- Confirmed Sysmon itself is working (SC-001 through SC-003's earlier steps
  all logged correctly), so this isn't a broken pipeline, it's a deliberate
  gap in this specific config.

## Root cause
The Neo23x0 Sysmon config used in this lab does not log schtasks.exe process
creation. This is a known, intentional trade-off in many public Sysmon
configs: scheduled tasks are extremely common in normal Windows operation,
so logging every one is noisy, but it means an attacker using
schtasks.exe for persistence would be invisible to this exact setup.

## Gap code
G1: no telemetry generated at all, at the Sysmon layer, before Wazuh ever
sees it.

## Fix
Enabled Windows' own Security auditing for scheduled tasks:
  auditpol /set /subcategory:"Other Object Access Events" /success:enable
This generates Event 4698 for scheduled task creation, regardless of which
tool creates it (schtasks.exe, PowerShell, COM API), which is more robust
than a Sysmon fix scoped to one binary name.

## Retest
Recreated a scheduled task. Event 4698 now arrives (channel: Security,
provider: Microsoft-Windows-Security-Auditing). Wazuh's own default
ruleset already covers it: rule 60228, level 4, mapped to T1053
(Scheduled Task/Job). No custom rule was needed — a custom rule (100011)
was initially written to fill what looked like a gap, but was found to
duplicate existing coverage once the correct data source was enabled, and
was removed.

## Note on Sysmon
The underlying Sysmon gap (schtasks.exe never logged) is unchanged and
still real. This fix works around it via a second telemetry source rather
than fixing Sysmon's config, which is a legitimate defense-in-depth
approach, not a full resolution of the Sysmon-side gap.
## Lesson
A working Sysmon pipeline (proven twice, in SC-001 through SC-003's setup and
in SC-002) does not guarantee every technique is covered. Config choices
create real, silent blind spots that only show up when you specifically
test for them.
